# Note Portal Windows x64 测试记录 — Issue #57，2026-09-28

测试对象为[公开 Release v0.1.1-alpha.1](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/releases/tag/v0.1.1-alpha.1) 的 x64 安装程序。测试机 Windows 11 Home 25H2，Build 26200.9457，x64；“关于”显示 Note Portal 0.1.1-alpha.1 · Windows；安装包 SHA-256：3D808646FA99577404FF1AC7D2661969F55722466368ECA72B67956FFA7B9930。Windows on ARM 未测。

## 范围与方法

- 安装包来自公开 Release，3,891,573 字节；SHA-256 与 #57 指定值及 Release 校验清单一致。安装后的程序 PE Machine=0x8664（x64），SHA-256 BFD0523E2B5EDD5C696B9016314C30D1D810E6A78DEA74B3B528BF8155E4ECE0。仓库 master 同步到 599ecc5；Release 标签对应 97c8a1d。没有使用 Actions 构建或 alpha.3。
- 主机为 20 个逻辑处理器、Edge WebView2 Runtime 153.0.4234.48、Chrome 153.0.8010.53。当前账户已有应用设置，安装程序执行覆盖安装；因此 A 组必须单独用新本地用户验证。
- 功能测试只写入公开示例库的临时副本、虚构文件、空目录和生成的性能样本。另有一篇本学期复习 Markdown 的本机字节一致临时副本用于阅读完整性抽查；未上传正文、私人绝对路径、阅读会话链接或截图。
- 标记为“人工”的项目由在桌面操作的测试者回报；其余项目由当前账户实机界面、Chrome 阅读页、文件哈希与本地进程观察核对。

## F：性能原始测量

按照 #57，F 组只记录数字与无法执行的原因。浏览器进程未计入；F1 计入主程序及其 WebView2 后代。关闭控制窗口并等待 1 分钟后采样 30 次、每次相隔 10 秒。

**F1，5 篇公开示例及临时图片文档：**

    进程数（末次）：7
    工作集合计：平均 433.5 MiB，最大 436.1 MiB
    私有内存合计：平均 200.4 MiB，最大 202.5 MiB
    平均 CPU：单核 0.21%，全部逻辑核 0.011%

**F2，同一小库，三次正常退出后启动至监听：**

    2.00 秒后本地服务开始监听
    2.69 秒后本地服务开始监听
    2.75 秒后本地服务开始监听

**F3，清单指定的 2,000 篇、251.2 MiB General 临时库：**生成数量和体积与清单相符；选择资料库的预览显示“资料库的 Markdown 总量超过 64 MiB；请分开选择较小的资料库”，确认按钮禁用，因而无法进行该规模的首次扫描、SSE、F1 或 F2。Release 源码的 Markdown 总量上限为 64 MiB（[library.rs](../src-tauri/src/library.rs)）。清单的 250 MiB 工作量与该上限不相容。

**F3 补充样本，2,000 篇、43.7 MiB：**同样的文件数，缩短每篇正文以低于 64 MiB。确认选择到“运行中”约 4.84 秒；由于 UI Automation 的确认操作同步返回，未能独立核实短暂的“启动中”文案和按钮禁用状态。同一文档连续三次保存至阅读页出现追加内容约 0.62、0.62、0.64 秒。这是端到端页面可见时间，不是开发者工具中的 SSE release 时间戳。

补充样本上的 F1 原始输出：

    进程数（末次）：7
    工作集合计：平均 617.4 MiB，最大 624.2 MiB
    私有内存合计：平均 348.6 MiB，最大 355.6 MiB
    平均 CPU：单核 0.34%，全部逻辑核 0.017%

补充样本上的 F2 原始输出：

    1.72 秒后本地服务开始监听
    3.42 秒后本地服务开始监听
    3.39 秒后本地服务开始监听

两个大库均已切出并删除。补充数据不能代替清单要求的 250 MiB 或 SSE 时间戳。

## 阅读完整性抽查与测试结束状态

- 公开 General 示例的笔记在实际阅读页可见正文。阅读器会将正文最外层首个 H1 移出文章区，以页面标题显示；这是 [reader/app.js](../reader/app.js) 中的显式行为，先前 #44 的 CRLF 测试因此出现“Heading 不在正文”的现象。
- 本学期一篇 50,439 字节的复习 Markdown 只以本机临时副本测试。应用识别为 1 篇；源文件 40 个一级至三级标题在 Chrome 辅助功能文本中均能找到。抽取正文首、中、末 9 个样本：原有折叠答案默认关闭时末尾 3 个不可见，展开“参考答案”后，忽略仍以字面显示的强调符号并归一空白，9/9 样本可找到。这个抽查没有逐字符验证整篇文档，也没有覆盖其他周。课程原件 SHA-256 未变，临时副本已删除。部分紧邻中文的 Markdown 加粗标记在阅读页以字面星号显示，正文字符仍在。
- 测试结束时，原来的临时 Study 库恢复为当前库，显示 3 篇笔记、服务运行；绿色主题、无 Logo、登录启动关闭且 Windows Run 项不存在。设置目录和文件仍为 Encrypted；两个故意损坏的设置由应用另存，不含用户笔记。含设置路径的本机安全副本已删除。没有修改课程笔记、公开示例原件或真实用户资料。
- A 组与 E1/E3 的人工结果收到后更新本记录。F3 的 250 MiB 工作量需先澄清 64 MiB 上限，才能按原清单完成。
