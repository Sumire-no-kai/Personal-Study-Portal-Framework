# Note Portal Windows alpha 实机测试计划

> [!IMPORTANT]
> **当前进行中的检查清单：[#57 Windows 1.0 正式版发布前检查清单](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/issues/57)。**测试哪个版本、谁测哪些项目、结果写在哪里，都以该 issue 为准；开始前先按 issue 开头核对安装包 SHA-256 和“关于”里的版本号。

本计划供另一台 Windows 电脑上的测试者执行，重点是 **Windows on ARM**。它验证已发布的安装包，不把 CI 编译成功当作安装、运行成功。测试者只记录问题；未经项目负责人要求，不修改源码、不提交 PR、不重新发布。

## 1. 先确认版本与机器

1. 从[公开 Releases](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/releases)下载要测试的版本，不用 CI 临时 artifact 代替正式下载路径。保存 Release 链接、标签、安装包完整文件名和 `SHA256SUMS.txt`。**发布检查清单优先：**如果有进行中的发布检查清单 issue（当前是 [#57](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/issues/57)；此前 0.1.1-alpha.1 用的是 [#44](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/issues/44)），就测该 issue 指定的版本（写在 issue 开头，或以最新评论为准），按该清单逐项测试，并把结果评论到该 issue；如果指定的是 Actions 构建，记录运行编号和提交号。这类构建没有 `SHA256SUMS.txt`，改为记录下载的产物和安装包的 SHA-256。
2. 用 PowerShell 的 `Get-FileHash -Algorithm SHA256` 核对安装包与校验文件。不一致就停止安装并报告。
3. 记录 Windows 版本与构建号、设备的处理器/系统架构、默认浏览器、是否已有 Edge WebView2 Runtime，以及测试前是否装过 Note Portal。
4. Windows on ARM 优先选择文件名含 `arm64-setup.exe` 的包。x64 包在 ARM 机器上即使通过模拟运行，也不能算原生 ARM64 验证。如果所选 Release 没有 ARM64 包，记录“ARM64 包未发布”，不要把 x64 结果写成 ARM64 通过。
5. Tauri 的 ARM64 NSIS 安装器外壳可能通过 x86 模拟运行，安装后的 Note Portal 应用主体仍应是原生 ARM64。安装器进程显示 x86 不是应用构建失败；应检查安装后的应用进程或可执行文件架构。

只在可信的测试机或虚拟机上处理未签名安装包。SmartScreen、杀毒软件或 WebView2 安装提示要截图记录；不要为了测试关闭系统防护，也不要在不信任的电脑上强行放行。

## 2. 使用可丢弃的测试资料库

不要选择真实笔记、课程资料、同步盘或生产目录。把仓库内的两个虚构示例**复制**到 Windows 临时目录，例如 `NotePortalQA` 下的 `general` 与 `study`：

- `servers/desktop-windows/examples/general-library-template/`
- `servers/desktop-windows/examples/study-library-template/`

选择的是各示例的**最外层文件夹**；Study 不要直接选择里面的 `content/`。测试前记录全部测试 `.md` 与图片的文件名、大小和 SHA-256；之后比较。只有明确点击“创建笔记”或“创建 Week 模板”时，才允许出现预览过的新文件；任何扫描、刷新、阅读、搜索和诊断都不应修改原文件。

测试缺陷时可以在这些**副本**里创建、编辑、重命名或删除测试文件；不要把这些操作施加到仓库原始示例上。

## 3. 必须测：安装与首次使用

| 编号 | 操作 | 预期 |
|---|---|---|
| W-01 | 安装 Release 中的 `.exe`，从开始菜单启动；记录安装器警告与是否需要管理员权限 | 安装完成，小控制窗口出现，不崩溃；默认浏览器是阅读界面，不是大应用窗口 |
| W-02 | 首次启动先不勾选同意；查看完整提示，然后点“不同意并退出”；再次启动 | 同意前不能选择资料库、启动服务或打开阅读器；退出后没有残留的本机监听服务；再次启动仍显示提示 |
| W-03 | 勾选并同意；检查“一分钟了解”对话框、“使用指南” | 引导说明 General/Study、选文件夹、浏览器阅读与外部工具更新 `.md`；不声称内置 AI |

## 7. 可选的第二轮检查

- 开启“登录电脑后在任务栏静默启动服务”，重新登录：服务可用但不自动弹浏览器；测试完恢复原设置。
- 测试端口被占用时“打开阅读器”仍可用；不要为此关闭其他用户进程。
- 在临时副本中测试无效 frontmatter、重复 `id`、过大的 Markdown/图片、指向资料库外的链接或符号链接：应诊断或拒绝，而不是泄露外部文件或破坏上一个有效页面。
- 记录应用空闲 5 分钟的 CPU、内存和启动耗时；浏览器与 Note Portal 进程分开记录。alpha 阶段先测量，不把 CI 编译成功当作性能达标。
- 以键盘完成主要按钮操作，并在 Windows 显示缩放 100% 与 150% 下查看小窗口、对话框、目录树是否能正常滚动和阅读。
- 最后卸载应用；临时资料库应保持原样。不要把用户设置是否删除当成笔记是否保留的替代证据。

## 8. 交回结果的格式

每项写 **通过 / 失败 / 未测**。失败项附：版本标签、Windows 构建号与架构、安装包名、复现步骤、实际/预期结果、截图或日志、是否只在 ARM64 出现。另给出安装器大小、应用进程架构、动态刷新耗时、空闲 CPU/内存。

不要在公开 Issue、仓库内的测试记录、截图或日志中暴露真实笔记正文、私人绝对路径、会话令牌、学校受限资料，以及本机 IP 地址、计算机名或 Windows 用户名。测试者可以报告必要的脱敏相对路径。

Windows on ARM 的 #57 公开 Release 补测见本文件末尾的“Issue #57 第一轮记录”。Windows x64 的 0.1.1-alpha.1 发布前 #44 构建复测见 [2026-09-25 Issue #44 记录](WINDOWS_X64_TEST_RUN_2026-09-25_ISSUE44.md)及修复设置写入后的 [#44 最终复测记录](WINDOWS_X64_TEST_RUN_2026-09-25_ISSUE44_RETEST.md)；alpha.3 公开安装包的 [2026-09-25 alpha.3 测试记录](WINDOWS_X64_TEST_RUN_2026-09-25_ALPHA3.md)与 [2026-09-23 alpha.1/alpha.2 记录](WINDOWS_X64_TEST_RUN_2026-09-23.md)保留作历史对照。逐项状态和测试机环境分别记在对应记录中。

### 原 F2 脚本复测及测量开销

每次正常 Quit 后，在独立 PowerShell 进程中运行 #57 原脚本，三次输出：

```text
3.08 秒后本地服务开始监听
2.93 秒后本地服务开始监听
3.03 秒后本地服务开始监听
```

平均 **3.01 秒**，原脚本数字仍超过 2 秒；旧构建此前同方法为 2.92、3.04、2.89 秒，平均 2.95 秒，仅凭这些数字无法看出 #62 的改进。

进一步在服务已经运行时启动新的 PowerShell，仅计时 `Get-NetTCPConnection -State Listen -OwningProcess`，三次查询都返回 1 个监听，但耗时依次为 **1.909、0.235、0.237 秒**。另一独立 PowerShell 显式加载 `NetTCPIP` 模块为 **0.683 秒**，之后首次查询为 **0.415 秒**。这些是不同会话的观察值，不能相加或从某次启动数字直接相减；说明首次模块加载、查询提供程序初始化和查询本身均可能污染原脚本计时，不能把 1.909 秒全部归为模块加载。

补充在同一 PowerShell 先调用一次端口查询，再按原启动脚本做三轮（轮间仍正常 Quit），输出 **0.89、1.16、1.05 秒**，平均 **1.03 秒**。这是预热测量工具后的补测，与独立 PowerShell 的原始结果分开记录，不能用它和旧构建原脚本数字直接计算产品加速比。

**结论修正：前节把原脚本输出超过 2 秒直接解释为应用服务启动超过预算，证据不足。保留原始数字，但应将其标为“含观察工具开销”；下面使用直接连接探针对比产品启动。**

### 相同直接探针：#62 前后对照

用同一 PowerShell/.NET 探针、同一账户/设置/库，启动已安装 EXE。计时前加载探针类型并预热 TCP 失败路径，确认保存端口未被占用；以 `Process.Start` 前的 Stopwatch 为零点，循环尝试连接保存的 loopback 端口，记录首次 TCP 成功，再发出不带会话凭据的 HTTP 请求，记录收到状态行的时间。探针不读取笔记或会话令牌；有效样本 HTTP 均为 **403**，符合未授权会话的保护逻辑，说明 HTTP 请求处理已在工作，**不等于阅读页首屏已渲染**。

每次连接最多等待 30 毫秒，失败后睡眠 10 毫秒，调度与连接调用还有额外开销。因此这些时间是探针观察到的时刻，具有轮询误差，不能视为精确的监听绑定时刻。进程创建时间通过测量结束后的系统进程元数据取得，未把查询开销计入 TCP/HTTP 时间；WebView2 创建时间是相对墙钟，不能代替控制器完成或窗口首屏时间。

### 底层原因与尚未量出的时间

1. **#62 前服务等待 WebView2 控制窗口创建。** [`main.rs` 的 `show_window`](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/blob/f39a214f70e2c14f98e44cc284feb30afb4baa34/servers/desktop-windows/src-tauri/src/main.rs#L1322) 调用 `WebviewWindowBuilder::build()`；旧 setup 先执行它，再派发已保存资料库的 `activate`。#62 在 [setup](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/blob/f39a214f70e2c14f98e44cc284feb30afb4baa34/servers/desktop-windows/src-tauri/src/main.rs#L1510) 先派发后台激活，再创建窗口，把两条路径重叠。新构建的 TCP/HTTP 时刻早于观察到的首个 WebView2 子进程，旧构建则相反；源码与实测共同支持“移除窗口创建对服务启动的前置等待”。本组节省的约 724 ms 是端到端差值，不能精确写成“WebView2 本身耗时 724 ms”。
2. **资料库扫描仍是服务监听的前置步骤。** [`server::start`](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/blob/f39a214f70e2c14f98e44cc284feb30afb4baa34/servers/desktop-windows/src-tauri/src/server.rs#L562) 先 `spawn_blocking(library::scan)` 并 await，再 `TcpListener::bind`、生成会话凭据/构建路由并启动 Axum，之后建立文件监控。`spawn_blocking` 避免阻塞异步工作线程，但不会让监听先于扫描完成。
3. **扫描成本随库增长。** [`library::scan_with_previous`](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/blob/f39a214f70e2c14f98e44cc284feb30afb4baa34/servers/desktop-windows/src-tauri/src/library.rs#L466) 遍历目录、稳定读取文件、解析 YAML frontmatter、生成文档/目录数据、计算 BLAKE3 签名；首次扫描也读取符合条件的图片并计算哈希。当前约 103 KiB 的 Markdown 小库不能代表大量文件、图片或网络盘；此处“49.40 ms”也不能全部算作扫描时间。
4. **端口响应不覆盖浏览器与首屏。** [`activate`](https://github.com/Sumire-no-kai/Personal-Study-Portal-Framework/blob/f39a214f70e2c14f98e44cc284feb30afb4baa34/servers/desktop-windows/src-tauri/src/main.rs#L889) 在 `server::start` 返回后保存设置、更新运行状态，再调用系统打开默认浏览器。探针可能早于这些步骤完成；Chrome 启动、阅读页网络请求、JS 执行和渲染都未分别计时。控制窗口启动后通过 Computer Use 核对了 Running / general / 6 documents / 0 notices，但没有精确测窗口首帧。
5. **原测量工具占用了明显时间。** 已运行服务上的首次端口查询仍耗时 1.909 秒，足以说明原 F2 中出现秒级工具延迟；服务启动、工具初始化可重叠，不能绘制各组件占原 3 秒的精确百分比图。直接探针和原脚本结果应并列保留，并在后续测试统一端点与测量方法。

当前二进制没有供本轮使用的内部启动阶段计时日志。要继续精确拆分，建议在后续诊断构建用同一单调时钟分别记录：setup 进入、settings/tray 完成、activate 派发/进入、scan 开始/结束、bind 完成、Axum 派发、watcher 完成、设置保存完成、浏览器打开调用开始/结束、WebView2 build 开始/结束、前端首次状态渲染。这些阶段存在并行，宜展示时间线；扫描再细分遍历、读取、解析与哈希并配合文件数/字节数，才能判断大库瓶颈。本轮没有修改运行代码，也没有以推测填补内部阶段数字。

### 本轮结论与结束状态

- **#62 的服务启动改进在当前 ARM64 设备、小型 General 库和已有缓存环境下得到直接对照支持。** 原脚本三次仍约 3 秒，属于含工具开销的结果；直接 TCP/HTTP 三次均远低于 2 秒。阅读器首屏、首次开机、大库和控制窗口完成时间未由这些数字验证。
- 主脚本 3 轮、预热查询 3 轮、直接探针对照 6 轮、恢复后 1 轮及运行库版本核对 1 轮共 **14 次有效启动**，均观察到控制窗口的正确状态并正常 Quit。诊断最初一次受限执行权限启动未产生窗口/服务，被结束后改用真实账户权限；该尝试无有效计时，未计入样本或据此判产品故障。
- 结束时恢复了 #62 对应主体哈希，正常 Quit 后应用进程 **0**、保存端口监听 **0**；主设置 SHA-256 与本轮安装前一致。原始脚本、查询开销记录、直接探针脚本和三组 JSONL 保存在本机测试工件目录；仓库仅同步本报告，不包含构建安装包、设置、会话凭据或笔记内容。
